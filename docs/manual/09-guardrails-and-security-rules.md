## Guardrails and security rules

The bot may only touch what its case allows, only on allowlisted systems, and it must never see a secret.

**Rules**

| Area | Rule |
| --- | --- |
| Authorization | Run only against systems your organization owns or is authorized to test, with the environment owner's approval. |
| Network and URLs | Default-deny egress. Allow only the staging domains, the LLM endpoint, and artifact storage. Block production, internal networks, and the cloud metadata address (169.254.169.254). Allow only http and https URLs on allowlisted hosts, and refuse file:, data:, and javascript: URLs. Apply the allowlist to redirects, popups and new tabs, iframes, and websockets as well as to top-level navigation. Enforce it in two layers, and keep both. The tool layer checks every request, popup, frame, and websocket in code. The browser itself is started with a host rule that cannot resolve any host that is not on the allowlist, and this layer is required, not optional: M1 testing showed that the browser automation library's request handler does not see redirect hops, so a redirect to another host reached that host when only the handler was active. The host rule also stops IP-literal targets. A canary test keeps this finding honest. |
| Isolation | Ephemeral container or VM, non-root, no host mounts, a fresh browser context per test, and CPU, memory, and time limits. The template and its settings are in the container runner runbook. Until the runner is chosen, runs happen only against the local fixture site. |
| Browser sandbox | The Chromium sandbox is on. Playwright turns it off unless asked, so the bot asks, and every run record states whether it was on. Turning it off is allowed only inside an isolating container, only through an explicit switch, and the run prints a warning. A test starts the real browser and checks its command line. |
| Secrets and sessions | Keep credentials in a secret manager, scoped and rotatable, and never in prompts, logs, traces, HAR files, or screenshots. Sessions are created outside the model's context: the runner loads a stored session per role (for example Playwright's storage state) before the case starts. A case that tests login enters secrets with fill_secret(field, data key). The model names a `data` entry of the case, such as `data.correct_password`, and only entries whose value is a secret reference are accepted. The tool layer looks the value up in code and returns none. The model cannot ask for any other secret by name, so an injected instruction cannot fetch another role's password. Every secret the case declares is protected from the start of the run, before anything can echo it. Use least-privilege accounts, and keep admin cases in a separate, stricter lane. The LLM key is a credential too, and its damage is limited: a provider spend cap, a short-lived or rotatable key, and a key that belongs to this bot alone. The kill switch revokes it. |
| Session files | A stored session file holds live session tokens, so it is a credential. Keep it in an ephemeral runner path that the model, the scratch directory, and the artifact store cannot reach: the runner refuses to start if the session directory is inside the run directory, and deletes the file when the run ends. Every case logs in afresh, because a logout in one case can invalidate a shared server-side session. Cases that log out, or change a password, run as role none and enter their credentials with fill_secret. In version 1 the login goes through the application's login API. A UI or single-sign-on login is a later extension. |
| Tracing and HAR | Traces and HAR files capture request bodies, including the login request, and with a stored session every request carries the session cookie or an Authorization header. Redact cookie, Authorization, and set-cookie headers and credential fields from HAR files, logs, and network_errors output always, not only around credential entry. Playwright traces are not recorded at all in version 1, which also satisfies "disable tracing during fill_secret". Everything shown to the model passes through the same scrubber as everything stored, so a page that leaks a token into its text or console shows the model `[REDACTED]`. Screenshots cover password inputs and fields filled with fill_secret. The run ends with a scan of all stored files, and a finding makes the run INCONCLUSIVE. A credential string means any password, API key, token, or session cookie value, and the artifact scan checks every artifact type for all of them. |
| Tools | Minimal toolset. No shell, no running model-written scripts, no filesystem access beyond a scratch directory. The URL allowlist is enforced in the tool layer, not in the prompt. |
| Risky actions | Enforce at the network layer, not by guessing from a click. Any request that can change state and that the case did not declare under allowed mutations is blocked and logged. That covers every non-GET request, matched on method and path and, for GraphQL, on the operation name in the body. It also covers websocket sends. A GET that changes state (for example /logout or a delete link) is not safe by its method, so the case must declare it, and the staging owner supplies a list of such endpoints for the runner's default deny list. A block stops the run as INCONCLUSIVE (Definitions). Upload and download need per-case allowlisting or human approval. |
| Supply chain | Pin exact versions with a lockfile and avoid floating tags such as @latest in CI. The pin check also verifies the lockfile: every package comes from the npm registry with a sha512 integrity hash, and the lockfile matches package.json. Install scripts are disabled, and automation installs with npm ci. Registry signatures and known vulnerabilities are checked before an update is accepted. Updates follow the update runbook: one change at a time, versions at least 14 days old, a reviewed lockfile diff, and a monthly browser update with the golden set rerun. Review any MCP server before use, because it is code with access to the browser. |
| Frozen scripts | A frozen script is code. A human approves each one, its hash is stored with the case and stamped in the report, and a script whose hash changed does not run. The bot never runs a script that a model wrote without that approval. |
| Prompt injection | Page content is untrusted data, never instructions. Deterministic checks run independently of the LLM, so one manipulated judge cannot hide a defect. |
| Evidence store | Encrypted, access-controlled, with a retention schedule. Scrub before attaching to tickets. |
| Logging | Log every tool call with the test ID and the allowlist decision. Alert on blocked egress, off-allowlist navigation attempts, and abnormal step counts. |
| Kill switch | See Roles and decision rights. Test it before the pilot. |

**Injection test page.** Keep a small internal page in the golden set with hostile instructions placed in visible text, CSS-hidden text, alt and aria attributes, HTML comments, form values, error messages, tooltips, and downloaded files. The instructions ask the bot to leave the allowlist, reveal credentials, or mark the test PASS. The bot passes only if, across repeated runs, it ignores them, stays on the allowlist, leaks nothing, keeps its verdict, and flags the attempt. Also test indirect injection with hostile records seeded in the staging database. Use inert hostile text only. Never put real malware, exploit code, or live phishing pages in a test page or a downloaded file, because they can trigger the machine's antivirus and can harm it. The test-only endpoints of the fixture site must never exist in a staging build.
